# Памятка агенту: GeoGuessr СПб

Этот файл — рабочая вводная для агента, который впервые открыл репозиторий.
Перед инфраструктурными или релизными изменениями обязательно прочитай также
`README.md` и `deploy/DEPLOYMENT.md`: там есть полные команды и процедура
одноразовой настройки production.

## 1. Что это за проект

«Петербургский следопыт» — небольшое server-rendered Flask-приложение без
фронтенд-сборщика. Игрок видит уличную панораму Яндекса, ставит точку на карте
Санкт-Петербурга и получает очки за расстояние до места съёмки. В игре пять
раундов, максимум 5000 очков за раунд.

Стек:

- Python 3.12, Flask, Flask-SQLAlchemy, Flask-Migrate/Alembic,
  Flask-Limiter, Gunicorn;
- SQLite по умолчанию (можно переопределить через `DATABASE_URL`);
- обычные HTML/CSS и браузерные ES-модули, без npm/bundler;
- Яндекс.Карты JS API v2 для панорам и клиентского геокодирования;
- Яндекс.Карты JS API v3 для карт и маркеров;
- pytest и Playwright/Chromium, причём E2E работают с локальной заглушкой
  Яндекс.Карт и не требуют сети или API-ключа.

## 2. Главное: два независимых сервера и две постоянные ветки

Проект работает по схеме:

```text
локальная работа / временная ветка
              ↓
        DEV: ветка dev
              ↓ push + ручная проверка
        origin/dev
              ↓ PR dev → main + GitHub CI
        origin/main
              ↓ PROD сам забирает main
       PROD: ветка main
```

Окружения:

- DEV: `https://dev.geoguessr.spb.ru`, закрыт Apache HTTP Basic Auth;
- PROD: `https://geoguessr.spb.ru`;
- `dev` — текущее состояние разработки и версия DEV;
- `main` — единственный источник версии приложения для PROD.

DEV и PROD **не делят состояние**. У каждого собственные `.env`, SQLite-база,
`venv`, секреты и локальные системные настройки. Они не передаются через Git и
не должны копироваться между серверами. Изменение или миграция DEV-базы ничего
не меняет на PROD.

GitHub Actions выполняет только CI. В workflow нет и не должно быть доступа к
PROD или deployment credentials. После merge в `main` production раз в пару
минут сам проверяет публичный `origin/main` по HTTPS и разворачивает новый
commit pull-based скриптом.

### Правила работы с ветками

1. В начале работы проверь `pwd`, `git branch --show-current`, `git status` и
   `git remote -v`; не полагайся на предположение об окружении.
2. Обычная разработка ведётся на DEV из `dev`. Небольшие изменения допустимо
   коммитить в `dev`; крупные — делать в `feature/*`, `fix/*` или `infra/*` от
   `dev`, затем вливать обратно.
3. Релиз — PR `dev → main`. Предпочтителен обычный merge commit, чтобы после
   релиза `dev` можно было синхронизировать через fast-forward:

   ```bash
   git switch dev
   git fetch origin
   git merge --ff-only origin/main
   git push origin dev
   ```

4. На PROD не разрабатывают: там должна быть ветка `main`, чистые tracked-файлы
   и HTTPS remote `https://github.com/kidavspb/geoguessr-spb.git`.
5. Не выполняй действий на PROD и не обходи `dev → PR → main`, если пользователь
   прямо не поручил production-операцию. Даже при таком поручении сначала
   сверяйся с `deploy/DEPLOYMENT.md`; миграции делают автоматический rollback
   потенциально опасным.

### Доступ к GitHub на DEV

Git remote использует SSH и репозиторный deploy key с правом push. Это не
авторизация GitHub CLI: `gh` на сервере не настроен, поэтому `gh pr create`,
`gh api` и другие команды GitHub API без отдельной авторизации не работают.

Для обычного `git fetch/push` не меняй remote и не запускай `gh auth login`.
Не читай, не копируй и не заменяй приватный ключ без прямого поручения. Если
нужен PR, подготовь ветку и ссылку для ручного создания PR либо запроси
отдельное разрешение на настройку GitHub CLI.

На PROD deploy key не нужен: deployment читает публичный `origin/main` по
HTTPS.

Текущий checkout этого рабочего каталога на 2026-08-27 — DEV: ветка `dev`,
remote по SSH, в `.env` стоит `FAVICON_VARIANT=dev`. То, что `dev` временно
опережает `main`, нормально до следующего релизного PR. Всегда перепроверяй
состояние: памятка может пережить перенос или смену ветки.

## 3. Как запрос доходит до приложения

На обоих публичных сайтах целевая цепочка одинакова:

```text
браузер → Apache :443 (TLS) → Gunicorn 127.0.0.1:8000 → Flask → БД
```

Apache-конфиги-эталоны лежат в `deploy/apache/`:

- `geoguessr-dev.conf` — dev-домен, Basic Auth и `X-Robots-Tag: noindex`;
- `geoguessr.conf` — production-домен без Basic Auth.

Apache передаёт `X-Forwarded-*`; Flask использует `ProxyFix` с доверием ровно
одному прокси. Поэтому Gunicorn должен оставаться привязанным к loopback, а не
быть напрямую доступным из интернета. Комментарий про nginx рядом с `ProxyFix`
в `app.py` исторический: фактический reverse proxy сейчас Apache.

На DEV установлен host-local unit `/etc/systemd/system/geoguessr.service`:
три Gunicorn worker, bind `127.0.0.1:8000`, `WorkingDirectory` и
`EnvironmentFile` указывают на этот каталог. Сам unit приложения не хранится в
Git. На DEV `AUTO_MIGRATE=false`, поэтому миграции применяются явно перед
рестартом. Docker — альтернативный способ локального запуска; его два worker с
`--preload` не описывают установленный DEV unit.

Production deployment состоит из:

- `deploy/systemd/geoguessr-deploy.timer` — периодический запуск;
- `geoguessr-deploy.service` — oneshot;
- установленной копии `geoguessr-deploy.sh` в
  `/usr/local/sbin/geoguessr-deploy`.

Deploy-скрипт консервативен: берёт `flock`, проверяет `main`, expected origin и
чистый working tree, допускает только fast-forward, ставит `requirements.txt`,
делает `flask db upgrade`, перезапускает приложение, проверяет
`http://127.0.0.1:8000/` и только затем обновляет marker успешного релиза в
`/var/lib/geoguessr-deploy/deployed-sha`. Если шаг упал, marker не меняется и
следующий timer повторит попытку. Автоматического rollback кода или БД нет.

Важно: файлы `deploy/apache/*` и `deploy/systemd/*` в Git — эталоны. Их merge
сам по себе не меняет Apache, systemd units или установленный deploy-скрипт на
PROD; инфраструктуру администратор применяет вручную.

## 4. Карта кода

- `app.py` — конфигурация Flask/БД, миграции, rate limiting, HTTP-роуты и
  сериализация ответов.
- `game_logic.py` — чистые константы и функции: генерация точек, haversine,
  формула очков, валидация координат и таймера.
- `models.py` — `GameSession`, `GameRound`, `VerifiedPoint`,
  `DailyChallenge`.
- `pool.py` — выбор, пополнение и самоочистка пула проверенных панорам.
- `daily.py` — общий набор точек на день по московскому времени.
- `stats.py` — фактическая сложность места по среднему промаху игроков.
- `geocoder.py` — опциональный серверный HTTP-геокодер. Сейчас игровой UI
  фактически получает адрес через клиентский v2 API и best-effort сохраняет его
  через `/api/game/set_address`; не считай импорт `reverse_geocode` в `app.py`
  доказательством, что он вызывается в основном request path.
- `templates/index.html` — все пользовательские экраны одной страницы.
- `templates/admin.html` — отдельная карта модерации пула.
- `static/js/main.js` — экраны и жизненный цикл игры.
- `static/js/panorama.js` — поиск/показ панорамы и prefetch следующего раунда.
- `static/js/maps.js` — карты выбора, результата и финала.
- `static/js/api.js` — таймауты и безопасные повторы HTTP-запросов.
- `static/js/state.js` — общее клиентское состояние и generation counters.
- `static/js/sdk.js` — повторное подключение упавших SDK Яндекса.
- `static/js/utils.js` — DOM, текст, метрика и меркаторская математика.
- `migrations/versions/` — единственная история production-схемы БД.
- `tests/` — backend/API тесты и E2E браузерные регрессии.

## 5. Серверная модель игры и основной поток

Сервер, а не cookie, является источником игрового состояния. Подписанная
Flask-cookie не зашифрована, поэтому в ней хранятся только `game_id` и маркер
daily-игры; координат ответов и прогресса раундов там быть не должно.

При `POST /api/game/start` создаётся `GameSession` и сразу пять `GameRound`:

- обычная игра берёт смесь точек пула и новых исследовательских точек;
- daily копирует общий набор текущей даты;
- challenge копирует точки и настройки завершённой игры автора.

Дальнейший поток:

```text
/api/game/start (в ответе уже location первого раунда)
  → клиент ищет ближайшую панораму v2
  → при реальном no coverage: /api/game/skip_location
  → после первого кадра: /api/game/ready
  → игрок ставит маркер на карте v3
  → /api/game/guess с round_id и точной позицией панорамы
  → сервер атомарно считает и сохраняет результат
  → ответ содержит next_location для фоновой подготовки следующего раунда
  → /api/game/results после пятого раунда
```

Ключевые инварианты:

- `round_id` защищает от запоздавших ответов старого раунда;
- повтор `/guess` идемпотентен и возвращает прежний результат;
- `location_version` делает повтор `/skip_location` идемпотентным;
- точная позиция найденной панорамы передаётся в том же `/guess`, чтобы не было
  гонки с отдельным best-effort запросом;
- позиция панорамы принимается только в пределах 1 км от серверной точки;
- сервер ограничивает skip десятью на раунд, клиент автоматически пробует до
  трёх замен;
- таймер стартует только после `/ready`, а не при выдаче координат/prefetch;
  сервер даёт 20 секунд grace на сеть;
- прогресс `current_round`, `answered_at` и `completed_at` меняется только в БД;
- лидерборд включает лишь завершённые игры.

Формула очков: 5000 в пределах 50 м, затем экспоненциальный спад
`5000 * exp(-distance_km / 3)`, ноль от 30 км. Режимы сложности различаются
распределением и радиусом точек, поэтому лидерборд умеет фильтровать их и не
должен молча считать режимы равнозначными.

## 6. Пул, daily, challenge и админка

Пул `VerifiedPoint` дедуплицируется по координатам, округлённым примерно до
10 м. Для обычной игры он включается при 15 подходящих точках: примерно 70%
раундов идут из пула, 30% продолжают исследовать новые места. Радиус пула от
центра: 3 км для `center`, 6.5 км для `medium`, без ограничения для `hard`.

Пустой успешный ответ `panorama.locate` означает `no_coverage`: такая точка
может получить fail и после трёх неудач удаляется из пула. Транспортный или SDK
сбой — `network_error`; он повторяется на той же точке и **не должен отравлять
пул**. Не объединяй эти ветки ошибок.

Daily создаётся лениво для даты МСК, всегда имеет `medium`, без таймера и
no-move. При достаточном пуле все пять точек подтверждённые. «Одна попытка в
день» сейчас привязана к cookie браузера, а не к аккаунту или глобальному
антифроду; незавершённая попытка возобновляется.

Challenge доступен только для завершённой исходной игры, наследует сложность,
таймер и no-move, а также копирует фактические координаты найденных панорам.

`/admin` существует только при заданном `ADMIN_KEY`. API админки требует
`X-Admin-Key` и использует constant-time сравнение; без ключа возвращает 404.
Интерфейс хранит введённый ключ в localStorage браузера. Никогда не печатай
секреты или содержимое `.env` в логи/ответы агента.

## 7. Особо хрупкие места фронтенда

Это важнее обычного style guide: здесь уже были реальные гонки и вылеты iOS.

- Одновременно должен жить минимум тяжёлых объектов Яндекса. Уничтожай Player
  и карты при уходе с экрана; лишние WebGL-контексты приводят к убийству вкладки
  на iPhone.
- У кнопки «Продолжить» намеренно только динамический `onclick` из
  `showRoundResult`. Не добавляй второй `addEventListener`: это запускает две
  параллельные загрузки следующего раунда.
- `roundLoadId`, `mainMapLoadId`, `resultMapLoadId`, `finalMapLoadId`,
  `modalLoadId` и `leaderboardLoadId` инвалидируют поздние Promise. Любой новый
  async flow должен соблюдать тот же принцип.
- Prefetch следующего раунда — одна переиспользуемая задача. Он делает один
  `locate` и прогревает до восьми дешёвых тайлов через `Image`; скрытый Player
  создавать нельзя.
- Медленный `/ready` не должен блокировать первый кадр или переход. Клиент
  запускает предварительный локальный deadline и уточняет его ответом сервера.
- На мобильном карта — нижний лист и стартует свёрнутой. Нельзя использовать
  fullscreen карты ценой пересоздания панорамы: игрок потеряет позицию.
- В no-move переход по стрелке откатывается событием плюс watchdog. Это UX-
  ограничение, а не криптографическая защита.
- CSS и entry-модуль получают `?v=<mtime>` и immutable cache; импортируемые
  ES-модули идут без query и ревалидируются благодаря
  `SEND_FILE_MAX_AGE_DEFAULT=0`. При добавлении важного ассета учитывай
  `inject_asset_version()`.
- DEV/PROD PWA-иконки выбираются только явным `FAVICON_VARIANT=dev`; любое
  другое значение безопасно означает `prod`.

## 8. БД и миграции

Рабочая SQLite лежит в `instance/`, игнорируется Git и не должна попадать в
diff, Docker image или тесты. Для SQLite включены foreign keys, WAL,
`busy_timeout=15s` и `synchronous=NORMAL`, поскольку несколько Gunicorn worker
могут писать одновременно. Rate limiter использует in-memory storage отдельно
в каждом процессе: это базовая защита от бытового abuse, не глобальный лимит.

После изменения `models.py` обязательно создай и просмотри Alembic-миграцию:

```bash
venv/bin/flask --app app.py db migrate -m "Описание"
venv/bin/flask --app app.py db upgrade
```

`db.create_all()` в pytest проверяет актуальные модели, но не доказывает, что
цепочка миграций работает. Для схемных изменений дополнительно проверь upgrade
с нуля на временной БД. Не запускай `db downgrade`, ручные SQL-правки или
автоматический rollback рабочей БД без отдельного обоснованного поручения.

Приложение умеет распознать старую БД времён `db.create_all()`, stamp-нуть
baseline `5f7875fb0c81` и продолжить Alembic upgrade. Не ломай этот путь без
проверки обратной совместимости.

## 9. Проверки перед передачей изменений

Минимум для любого изменения кода:

```bash
venv/bin/pytest -q
git status --short
git diff --check
```

`pytest` запускает backend и E2E. Если Chromium ещё не установлен:

```bash
venv/bin/python -m playwright install chromium
```

E2E поднимают отдельный Flask-процесс на временной SQLite, перехватывают SDK
Яндекса локальной заглушкой и не используют production/DEV базу. Backend
fixtures также задают временный `DATABASE_URL` до импорта `app.py`.

Для инфраструктурных изменений дополнительно:

```bash
bash -n deploy/systemd/geoguessr-deploy.sh
```

Для изменения игрового потока, панорам, карт или async-кода обязательно смотри
`tests/e2e/test_flow.py`; там зафиксированы отсутствие лишних location/locate,
один живой Player, no-move, fallback после no coverage, сетевой retry без skip,
закрытие позднего modal Player и неблокирующий `/ready`.

На DEV после миграции и рестарта сделай smoke-check
`https://dev.geoguessr.spb.ru` под Basic Auth. Не выводи пароль из `.env` в
транскрипт. Не считай изменение готовым к `main`, пока CI и ручная проверка DEV
не прошли.

## 10. Практические границы изменений

- Сохраняй пользовательские незакоммиченные изменения и сначала исследуй
  грязный working tree.
- Не редактируй `.env`, рабочую БД, `/etc/apache2`, `/etc/systemd/system` или
  установленный `/usr/local/sbin/geoguessr-deploy`, если задача явно не про
  соответствующую локальную/инфраструктурную настройку.
- Правка шаблона инфраструктуры в Git и применение его на сервере — два разных
  действия. Всегда сообщай, какой из шагов сделан.
- Не делай push, PR, merge в `main` или production deploy только потому, что
  код готов: это отдельные внешние действия, которые должны следовать задаче
  пользователя и описанному release flow.
- Если документация расходится с исполняемым кодом или установленным конфигом,
  сначала зафиксируй конкретное расхождение. Для текущей логики истина — код и
  тесты; для релизного процесса — `deploy/DEPLOYMENT.md` плюс фактическое
  состояние соответствующего сервера.
