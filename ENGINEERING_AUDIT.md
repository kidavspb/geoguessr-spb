# Инженерный аудит — 10 сентября 2026

Исходная версия: `ddbf611`, чистая ветка `dev`, актуальная относительно
`origin/dev` и содержащая `origin/main`. Работа выполнена локально в
`fix/codebase-audit`. Push, PR, restart и production-операции не выполнялись.
Рабочие `.env`, БД и venv не изменялись.

## Охват и устройство системы

Просмотрены production-модули Python, браузерные ES-модули, оба HTML-шаблона,
CSS, история миграций, maintenance-скрипты, конфигурация Docker, Apache,
systemd, CI и документация. Проверены потребители подозрительных функций,
динамические обращения из JS/HTML и тесты основных инвариантов.

| Область | Ответственность и вывод |
|---|---|
| `app.py`, `models.py` | HTTP, конфигурация, серверное состояние. Крупный файл, но добавление service/repository-слоёв сейчас не окупается. |
| `game_logic.py`, `districts.py` | Расчёты и пространственные ограничения. Prepared geometry, кэши и выбор частей MultiPolygon пропорционально площади обоснованы. |
| `pool.py`, `daily.py`, `stats.py` | Повторное использование панорам, общий набор дня, агрегаты промахов. Порог пула и доля exploration сохранены. |
| `main.js`, `state.js` | Экраны и ход игры. Прямое общее состояние приемлемо для размера проекта; главная сложность — асинхронные переходы. |
| `panorama.js`, `maps.js`, `sdk.js`, `api.js` | SDK, сетевые операции и жизненный цикл ресурсов. Разделение no coverage/network error и уничтожение Player критичны. |
| `districts.js`, CSS | Локальный SVG-selector, zoom/pan/touch и адаптивность. Большая часть сложности объясняется реальными браузерными ограничениями. |
| Deployment | CI проверяет код; PROD читает main по HTTPS. Шаблоны инфраструктуры не применяются автоматически. |
| Тесты | Backend работает на временной SQLite; E2E поднимает отдельный процесс и перехватывает SDK Яндекса. |

Основной поток: `/start` создаёт пять строк раундов → locate в браузере →
проверка фактической точки для district/hard → `/ready` → `/guess` → результат
и подготовка следующей панорамы → `/results`. Cookie хранит идентификатор
игры, а координаты, результаты и прогресс находятся в БД.

## Что изменено и почему

### Исправленные баги

| Проблема до изменения | Последствия | Исправление и проверка |
|---|---|---|
| Два workers читали один несыгранный раунд до commit | Второй guess мог переписать первый ответ; параллельные skips выдавали разные точки; skip мог заменить уже сыгранную точку | Блокировка записи игры перед чтением состояния. Три теста перекрывающихся запросов воспроизвели ошибку и прошли после изменения. |
| Версия кандидата проверялась не во всех мутациях | Старые ready/guess/metric после skip могли начать таймер, принять ответ или записать метрику другой точки | `location_version` передаётся клиентом и проверяется сервером также в этих трёх операциях. Повтор уже принятого guess по-прежнему возвращает сохранённый результат. |
| Скалярный/массивный JSON, нечисловые и чрезмерные ID | 500 либо непреднамеренное действие над текущим раундом | Общий разбор JSON-объекта и целочисленных полей; 400 до изменения состояния. Пустое тело старых start/skip осталось допустимым. |
| Числовые переполнения и bool в координатах | Исключения при преобразовании либо принятие true как широты 1 | Явная валидация, обработка OverflowError. Неизвестная строковая сложность продолжает нормализоваться в medium. |
| Погрешность haversine у противоположных точек | `sqrt(1-a)` мог получить отрицательное число | Ограничение промежуточного a диапазоном [0, 1]; отдельная проверка противоположных точек. Формула очков не менялась. |
| Не-ASCII заголовок админ-ключа | `compare_digest(str, str)` выбрасывал TypeError | Сравнение UTF-8 bytes; неверный ключ возвращает 403. |
| Ошибка GET location до получения кандидата | Видимая кнопка «Повторить» ничего не делала | При отсутствии точки повтор заново запрашивает location; старый кандидат очищается. E2E с двумя HTTP 503 и восстановлением. |
| Ошибка `/results` | Показ пустого финала или DOM предыдущей игры; отсутствие повтора | Финал открывается после успешного ответа. При ошибке сохраняется результат последнего раунда и доступен повтор. E2E с восстановлением после 503. |
| SDK загрузился, но ready не завершился | Бесконечное ожидание вопреки объявленному таймауту | Конечный таймаут и новая попытка загрузки SDK. E2E отдельно для v2/v3 с управляемыми часами. |
| Уже истёкший deadline при запуске таймера | После синхронной остановки создавался новый интервал, повторяющий timeout | Интервал создаётся до первой проверки времени. E2E проверяет единственный запрос guess после нескольких тиков. Отложенный сетевой повтор также привязан к поколению и ID раунда. |
| Выделение другой точки во время DELETE в админке | Сервер удалял запрошенную точку, а интерфейс убирал новый выделенный маркер | ID сохраняется до await и используется после ответа. E2E с задержанным DELETE. |
| Разные группы игр в числителе/знаменателе completion rate | Завершённые старые игры завышали доигрываемость, потенциально выше 100% | Доля считается среди игр, начатых за семь дней. Отдельные счётчики начатых/завершённых за период сохранены. |

Блокировка реализована коротким UPDATE, сохраняющим прежнее значение поля.
Он выполняется до SELECT: SQLite начинает транзакцию записи, PostgreSQL
блокирует строку. Обычные GET эту блокировку не берут. Механизм опирается на
БД, поэтому действует между workers, в отличие от Python mutex. Основание:
[SQLite transactions](https://www.sqlite.org/lang_transaction.html),
[PostgreSQL explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html).
На PostgreSQL проверка выполнена по документации, интеграционный прогон был
только на SQLite. На SQLite одновременно пишет один запрос; при росте истории
нужно измерять время удержания блокировки, особенно для статистики `/guess`.

`mark_point_failed(commit=False)` больше не может молча откатить транзакцию
вызывающего skip и продолжить его без блокировки. Ожидаемые ошибки БД в пуле
обрабатываются как SQLAlchemyError, конфликт создания daily — IntegrityError.
Ошибки программирования больше не маскируются под обычный конфликт записи.

  устаревшие упоминания ключа. Последний рабочий вызов HTTP-геокодера удалён
  коммитом `8142742`; поиск по всему репозиторию не выявил других потребителей.
  Клиентский геокодер и сохранение адресов продолжают работать.
- Неиспользуемый `district_metadata`, избыточная JS-обёртка имени района,
  неиспользуемый аргумент peek в клиенте. Сам GET location сохранён: он нужен
  для восстановления, а старый URL с peek остаётся рабочим.
- Реэкспорты из `app.py`, существовавшие только ради тестов. Чистые функции
  теперь тестируются через `game_logic` без инициализации Flask; тесты пула
  импортируют `pool` непосредственно.
- Fallback-код Flask-SQLAlchemy < 3 и старого SQLAlchemy в `migrations/env.py`:
  проект использует закреплённый Flask-SQLAlchemy 3.1.1. Сами ревизии не
  переписывались; проверены upgrade и распознавание базы без Alembic.
- Разрозненные повторные CSS-блоки `.result-pano` и hover карты объединены.
  Размеры, цвета, breakpoints и визуальное поведение не менялись.
- Из deployment-документа удалены устаревшие поручения повторить уже
  завершённый переход `infra/dev-and-deploy`. Одноразовая настройка нового
  PROD и обычный release flow сохранены.

Общий таймаут операций SDK находится в `sdk.js`, поиск точки пула по ключу
использует один helper. Новых архитектурных слоёв и runtime-зависимостей нет.

## Зависимости

Все восемь прямых runtime-зависимостей нужны: Flask/Werkzeug обслуживают HTTP,
Flask-SQLAlchemy — ORM, Flask-Migrate — миграции, Flask-Limiter — ограничения,
python-dotenv — конфигурацию, Gunicorn — сервер, Shapely — геометрию.
Крупной библиотеки, используемой ради тривиальной операции, не обнаружено.

`pip check` прошёл. `pip-audit` проверил 42 установленных пакета: в замыкании

## Что сознательно не менялось

- Географические границы, подбор района, распределение точек, zoom/pan,
  no-move, пять раундов, scoring и серверный grace таймера.
- Cookie-based daily, правила challenge и возможность индивидуального skip.
  Общий набор при редком отсутствии покрытия может расходиться; это требует
  продуктового решения, а не скрытого изменения во время рефакторинга.
- `set_actual_point`, отсутствие обязательного round_id у старых клиентов,
  запуск таймера в legacy guess без ready, совместимость старых hard challenge.
  Нет данных об активных старых вкладках и сохранённых играх, чтобы безопасно
  удалить эти контракты.
- Rollout guard районного UI, ревалидация ES-модулей, reload шаблонов,
  no-move watchdog, fallback открытия Player, уничтожение поздних Player и
  единая prefetch-задача. История и E2E подтверждают их назначение.
- Статический каталог районов в HTML. Перевод на новый template context
  ломал бы рендер у старого worker между pull и restart. Защита rollout важнее
  удаления небольшого дублирования.
- Схема БД, ревизии миграций, API routes, DEV/PROD branding и инфраструктура.
  В `models.py` исправлены только комментарии; `flask db check` не нашёл
  изменений схемы.

## Оставшийся технический долг

### Стоит сделать

1. **Явно отвергать небезопасный SECRET_KEY при production-запуске.** Сейчас
   отсутствие переменной приводит к общеизвестному fallback-ключу. Это риск
   подделки cookie при ошибке настройки, а не обнаруженная утечка реального
   секрета. Нужен согласованный контракт локального запуска; секрет PROD не
   проверялся и не менялся.
2. **Разобрать advisories инструментов разработки.** Для pytest проверить
   исправление upstream и использовать приватный временный каталог или
   изолированного пользователя; Pillow/pip обновлять отдельно с проверкой
   maintenance-команд. Не принимать `fix_versions` сканера за доказательство.
3. **Добавить защиту поколениями во второстепенные async-пути.**
   `loadPlayerStats` и `showDailyTop` могут отобразить поздний ответ предыдущего
   финала. Админке нужны обработка сетевых исключений, ожидание готовности
   карты перед ручной загрузкой и восстановление при недоступном localStorage.
4. **Определить судьбу обязательных round_id/location_version.** Новые клиенты
   их отправляют, но legacy fallback сохраняет менее строгую защиту. Сначала
   нужна наблюдаемость использования старого контракта и срок поддержки.

### Можно сделать при подтверждённой потребности

- Измерить стоимость агрегации всей истории в `difficulty_percentile` и
  случайной сортировки пула. Кэш или агрегатная таблица оправданы после
  измерений объёма и latency, а не заранее.
- Согласовать округление координат в `stats.py`: Python round использует
  округление половин к чётному, SQL round может давать другой ключ ровно на
  границе ячейки. Не менять существующие ключи пула без анализа данных.
- При обновлении GeoJSON предусмотреть переклассификацию уже заполненных
  `VerifiedPoint.district_id`. Текущая миграция намеренно backfill-ит только
  NULL; сохранённый spatial cache нельзя считать вечным при смене dataset.
- Отделить настройки/лидерборд от `main.js`, если появится следующая крупная
  функция. Сейчас большое перемещение кода не устраняет конкретного бага.
- Уточнить поддержку PostgreSQL: выбор драйвера, миграции и интеграционный CI.
  Возможность задать DATABASE_URL не означает проверенную поддержку всех СУБД.
- E2E fixture использует фиксированный порт 5688 и прячет stderr сервера.
  Для параллельных прогонов нужны отдельный порт и диагностика старта.

### Скорее не стоит трогать

Переписывать Flask в другой framework, добавлять repository/DI-слои,
заменять Shapely собственным point-in-polygon, вводить bundler ради этих
изменений, менять pull-based deployment или убирать исторические Alembic
ревизии. Два SDK Яндекса здесь обслуживают разные необходимые функции.
